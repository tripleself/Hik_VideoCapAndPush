# **轨道打磨车视频显示同步切换系统 - 技术方案文档**

**版本**: 1.0
**日期**: 2025年8月25日

## 1\. 项目概述

本项目旨在解决轨道打磨车双端司机室视频显示系统的同步问题。打磨车在一位端和二位端各配备一部双光源摄像机，所有视频及控制信号均汇集至位于一位端司机室的中央工控机。工控机对视频进行后处理，并分别推送至两端司机室的触屏电脑进行显示。

当前需求是，无论操作员在哪一端司机室，都能通过简单的界面操作，使两端的触屏电脑**同步显示**由车辆前进方向决定的摄像头画面，即“哪端前进，显示哪端”。

本文档将详细阐述实现此功能的目标、需求、技术方案及实施计划。

## 2\. 任务目标与需求

### 2.1 总体目标

建立一套稳定、高效的通信协调机制，实现打磨车两端司机室显示屏视频源的实时、同步切换，以满足实际作业过程中的安全监控与操作需求。

### 2.2 核心功能需求

1. **显示同步**: 在任何时刻，一位端和二位端的触屏电脑必须显示完全相同的视频画面。
2. **方向关联**: 显示的视频源必须与车辆的前进方向严格对应。
   * 当车辆以一位端为前进方向时，两块屏幕都显示一位端摄像头的后处理视频。
   * 当车辆以二位端为前进方向时，两块屏幕都显示二位端摄像头的后处理视频。
3. **双端控制**: 任意一端的司机都可以通过触屏电脑上的前端程序UI按钮（Screen_Code.ui中的"endpointbutton"按钮）发起切换指令，该指令的效果对两台触屏电脑同时生效。
4. **系统集成**: 新增功能必须无缝集成到现有系统中，特别是**不得修改工控机后端现有的四路视频流（一位端可见光、一位端热红外、二位端可见光、二位端热红外）持续推送的稳定架构**。切换逻辑应在客户端执行。
5. **低延迟**: 从操作员点击切换按钮到两块屏幕完成画面切换的整个过程，应在视觉上达到“瞬时”效果，延迟应在毫秒级别。

## 3\. 系统环境

### 3.1 硬件部署环境

| 设备名称         | 数量 | 位置                 | 连接方式                           |
| :--------------- | :--- | :------------------- | :--------------------------------- |
| 中央工控机 (IPC) | 1    | 一位端司机室         | 作为系统核心，通过网线连接所有设备 |
| 双光源摄像机     | 2    | 一位端、二位端车头   | 通过网线接入工控机                 |
| 触屏电脑         | 2    | 一位端、二位端司机室 | 通过网线接入工控机                 |
| 车辆数据箱       | 1    | 车体                 | 通过RS422串口连接至工控机          |

### 3.2 软件与开发环境

* **操作系统**: 所有设备（工控机、触屏电脑）均为 `Windows 10`。
* **编程语言**: 所有后端（工控机）和前端（触屏电脑）程序均使用 `C++` 编写。
* **网络协议**: 设备间通信基于 `TCP/IP` 协议，利用现有的局域网环境。

## 4\. 技术实施方案

### 4.1 总体架构：服务器协调，客户端执行

本方案将复用现有工控机（服务器）与触屏电脑（客户端）之间已建立的TCP长连接。工控机作为**中央协调器**，负责接收切换请求并广播统一指令；客户端负责接收指令并**本地执行**视频流的切换动作。

**数据流与控制流示意图:**

```
+------------------+     (1) 发送切换请求     +-----------------+
| 触屏电脑A (Client) | ---------------------> |                 |
+------------------+   "CMD:SET_DIR:2"       |                 |
                                             | 工控机 (Server) |
+------------------+     (2) 广播切换指令     |   协调中心      |
| 触屏电脑B (Client) | <--------------------- |                 |
+------------------+   "NOTIFY:SHOW_DIR:2"   |                 |
        ^                                    +-----------------+
        |                                       ^
        +---------------------------------------+
                (2) 广播切换指令 "NOTIFY:SHOW_DIR:2"
```

### 4.2 通信协议设计

在现有的TCP数据流中，引入统一格式的文本指令，通过添加“标签”前缀来区分不同类型的消息。

* **车辆数据 (已有)**: `DATA:<payload>`
  * *示例*: `DATA:SPEED:80;KM:123.4`
* **客户端切换请求 (新增)**: `CMD:SET_DIR:<direction>`
  * `<direction>`: `1` 代表一位端，`2` 代表二位端。
  * *示例*: `CMD:SET_DIR:1`
* **服务器广播通知 (新增)**: `NOTIFY:SHOW_DIR:<direction>`
  * `<direction>`: `1` 代表一位端，`2` 代表二位端。
  * *示例*: `NOTIFY:SHOW_DIR:2`

*注：为保证消息接收的完整性，建议每条指令以换行符 `\n` 结尾。*

### 4.3 服务器端 (工控机) 实现方案

**目标**: 修改现有TCP服务器程序，增加指令处理与广播功能。

1. **管理客户端连接**:

   * 维护一个线程安全的客户端 `SOCKET`列表（如 `std::vector<SOCKET>`），并使用 `std::mutex` 进行保护。
   * 在客户端连接和断开时，动态更新此列表。
2. **实现指令广播功能**:

   * 创建一个 `BroadcastCommand(const std::string& command)` 函数。
   * 该函数将锁定客户端列表，遍历所有已连接的 `SOCKET`，并向它们发送传入的指令字符串。
3. **修改消息接收逻辑**:

   * 在接收并处理客户端消息的循环中，增加对 `CMD:SET_DIR:` 指令的解析。
   * 当收到此指令时，服务器**不执行任何本地操作**，而是立即调用 `BroadcastCommand` 函数，向所有客户端广播对应的 `NOTIFY:SHOW_DIR:` 指令。

### 4.4 客户端 (触屏电脑) 实现方案

**目标**: 修改前端显示程序，增加指令发送和视频源切换功能。

1. **发送切换请求**:

   * 为UI界面上的“一位端前进”和“二位端前进”按钮绑定事件处理函数。
   * 在事件处理函数中，通过已建立的TCP连接，向服务器发送格式化的 `CMD:SET_DIR:` 指令。
2. **接收并处理广播指令**:

   * 在客户端接收服务器消息的循环中，增加对 `NOTIFY:SHOW_DIR:` 指令的解析。
   * 当收到此指令时，调用本地的视频切换函数。
3. **实现本地视频源切换**:

   * 创建一个 `SwitchVideoSource(int direction)` 函数。
   * 此函数将根据传入的 `direction` 参数（1或2），控制视频播放器（如使用FFmpeg, VLC, 或自定义解码器）停止播放当前视频流，并开始连接和播放新的视频流。
   * 例如，从 `rtsp://<IPC_IP>/cam1_visible` 切换到 `rtsp://<IPC_IP>/cam2_visible`。由于工控机始终在推送所有四路视频流，此切换过程将非常迅速。

## 5\. 总结

本方案在充分利用并尊重现有系统架构的基础上，通过引入一个轻量级的“服务器协调”通信机制，巧妙地解决了双端视频同步切换的需求。该方案具有**实现简单、风险低、对原系统侵入性小、性能高效**等优点，能够快速、稳定地完成项目目标。
